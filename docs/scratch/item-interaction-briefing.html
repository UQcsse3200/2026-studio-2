Item Interaction — everything to know before you explain it

One page covering what got built, how it works, what it's still missing, and exactly what to say to the UI team, your own team, and anyone reviewing the ticket.

01Summary

The one-paragraph version, for when someone asks "so what did you actually do?"

PlayerInteractionComponent lets the player pick up, drop, delete, and switch items using the keyboard. It scans the world for the nearest item within a fixed range, re-checks that range and the item's availability at the moment of interaction (not just when first detected), and rejects anything invalid without crashing — a full inventory, an out-of-range item, or nothing to interact with all just fail quietly and fire an event.

02Interaction flow

The actual sequence, end to end — this is a real order, not a arbitrary list.

  1. Player presses a key Keyboard input fires a named event (interact, dropItem, etc.) — see the key map below.
  2. Nearby items get scanned findNearestItem() looks at every registered entity, keeps only the ones carrying an ItemComponent, and picks the closest one.
  3. Range gets checked — again Even though the item was just found "in range," pickup() re-validates distance before acting, since the player or item may have moved.
  4. Availability gets checked Confirms the target still has an item to give (not already collected, not a stray entity).
  5. Inventory decides success or failure InventoryComponent is asked to add/remove the item — it can refuse (e.g. full), and that refusal is respected, not overridden.
  6. An event fires either way Success and failure both notify the rest of the game (UI, audio, anything listening) — nothing fails silently.

Interaction range is a constant: 1.5 metres. Worth knowing if anyone asks why an item "didn't work" — it's almost always distance.

04What level is this code?

In case it comes up: this is intermediate, not beginner, and not over-engineered either.

Why it's not beginner

  • Each action is its own small method, not one giant function
  • Every invalid case is handled — nothing crashes on bad input
  • Follows the codebase's own existing pattern (TouchAttackComponent)
  • 13 tests cover both success and failure paths

Why it's not over-built

  • No custom design patterns, no framework, no premature abstraction
  • Item search is a plain linear scan — fine at this game's scale
  • Same simple event style already used everywhere else in the project

05What to tell the UI team

They don't build detection or validation — they just react to it.

Say this

"You don't need to build anything for pickup/drop/delete — just listen for these events on the player and show whatever feedback makes sense (toast, sound, animation). The inventory bar at the bottom already auto-updates on its own, that's not new."

  • itemPickedUp → confirmation, maybe a "+1" popup
  • itemPickupBlocked → "Inventory full" message
  • itemDropped / itemDeleted → confirmation feedback
  • If they want an on-screen "Press E" prompt, the trigger distance is 1.5m

06What to tell your own team

Say this
  • Built: pickup / drop / delete / switch, all range-validated, all safe on bad input
  • Lives on branch feature/player-item-interaction, built on top of feat/item&inventory
  • Blocker: can't reach main until the item/inventory branch is merged first
  • 13 unit tests pass, full suite (100+ tests) still green — no regressions
  • Not yet manually playtested in a running game window

Two bugs found in the item/inventory branch — worth flagging

  • Item folder is capitalized (Item/) but its package is lowercase (item) — works on Windows, can break the build on Linux CI
  • One test file sits in the wrong package folder (player instead of inventory)
